## 1. Technical Explainer: Workflows, Agents, & Model Context Protocol (750 Words)

### Section A: The Fundamental Distinction — Workflow vs. Agent

In modern artificial intelligence engineering, "agent" has become one of the most frequently misused terms. Marketing copy often labels simple multi-step prompts as autonomous agents. However, Anthropic's engineering framework (*Building Effective Agents*) establishes a clear, rigorous distinction based on control flow and autonomy.

A **Workflow** is an orchestrated system where large language models (LLMs) and code are organized into deterministic, pre-defined execution paths. In a workflow, human developers hardcode the sequence of steps, branch conditions, and data handoffs. For example, a prompt chain that parses code (Step 1), audits accessibility (Step 2), generates tests (Step 3), and formats markdown (Step 4) is a workflow. The LLM performs intelligence work at each individual node, but it has no autonomy to skip steps, alter the sequence, or decide when the job is complete. The system's control flow is entirely static.

An **Agent**, by contrast, is a dynamic system where an LLM autonomously directs its own control flow and tool selection in an environment loop. Given a high-level goal, an agent evaluates environmental feedback, decides which tools to invoke from an available toolkit, inspects tool outputs, diagnoses errors, and repeats the cycle until it determines the goal has been satisfied. The defining characteristic of an agent is runtime decision-making: the sequence of actions is not pre-written by a developer, but dynamically generated by the LLM in response to real-time feedback.

Applying this distinction to our FL-04 build ("Draft, Critique, Revise & Test Engine"), **FL-04 is strictly a WORKFLOW** (specifically a *Prompt Chain / Orchestrator-Workers Workflow*). The data flows linearly through hardcoded XML tags (`<component_ast>` → `<accessibility_audit>` → `<production_files>`). The model does not choose its next action or decide to run external commands on its own initiative; it simply executes the step specified by the pipeline orchestrator.

### Section B: Model Context Protocol (MCP) & The Three Primitives

For an LLM or agent to perform meaningful work beyond conversational text, it requires access to external data, systems, and tools. Historically, connecting an LLM to a database, local filesystem, or API required building custom, proprietary integrations for every application. 

The **Model Context Protocol (MCP)** is an open open-standard protocol—frequently referred to as the "USB-C port for AI applications"—that provides a universal, standardized interface for models to securely interact with local tools, environments, and data repositories.

MCP operates on three core client-server primitives:

1. **Tools**: Callable functions exposed by an MCP server that allow the model to perform side-effect actions in the external environment. Examples include `run_command` (executing terminal shell scripts), `view_file` (reading local source code), and `write_to_file` (creating disk artifacts).
2. **Resources**: Read-only data sources and context streams exposed to the model. Resources provide environment state, such as active git branch metadata, database schema declarations, or live server log feeds, without executing side effects.
3. **Prompts**: Pre-configured prompt templates and reusable instruction sets exposed by servers to standardize complex user interactions.

By establishing a clean abstraction layer, MCP enables AI applications to discover tools dynamically, request permission before side-effect execution, and safely manipulate real-world software development environments.

### Section C: Concrete Agent Upgrade — Transforming FL-04 into an Autonomous Agent

To transform our FL-04 linear workflow into a true autonomous agent, we must replace the static 4-step sequence with an **Evaluator-Optimizer Loop Agent** equipped with MCP tools.

Currently, if Step 3 generates a Vitest test suite with a syntax error or a failing assertion, the workflow stops and requires human intervention to fix the test. 

To upgrade FL-04 into an **Autonomous Test-Fixing Agent**:

1. **Tool Equipping**: The agent is provided with three MCP tools: `view_file` (read code), `replace_file_content` (edit code), and `run_test` (executes `vitest run` in the terminal).
2. **Autonomous Loop Execution**:
   - *Goal*: "Build accessible React component `SettingsForm` with 100% passing Vitest test coverage."
   - *Action 1*: Agent drafts initial code and test suite using `replace_file_content`.
   - *Action 2*: Agent invokes `run_test` via MCP connector.
   - *Evaluation*: If `run_test` fails, the agent receives the exact CLI error stack trace as environmental feedback.
   - *Optimization*: The agent analyzes the failure (e.g., missing `aria-invalid` attribute), modifies `SettingsForm.tsx` via `replace_file_content`, and calls `run_test` again.
3. **Termination Condition**: The agent loops autonomously until `run_test` returns a 0 exit code (all tests passing), requiring zero human intervention during execution.
